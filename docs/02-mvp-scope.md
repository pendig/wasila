# MVP Scope

## First Profile

The first supported profile is `startup_saas`.

This profile represents a small software company handling product questions, onboarding issues, bug reports, technical support, customer success, and owner escalation.

## First Agents

### Front Office Agent

Receives the initial customer message, identifies intent, asks for missing context, and decides whether the message should be answered directly or routed to another agent.

### Ticket Manager Agent

Creates, updates, and summarizes tickets. This agent is responsible for preserving operational trace, ticket status, priority, and next action.

### Technical Support Agent

Handles product, bug, account, integration, and technical questions for the `startup_saas` profile.

### Owner Agent

Produces concise owner-facing summaries for important customer interactions. This agent is required in every profile.

## First Gateways

The MVP uses a generic HTTP webhook as the first gateway type.

Wasila separates gateways by audience:

- Customer gateways receive and respond to customer conversations.
- Owner gateways send owner summaries, alerts, and approval requests.

The first customer gateway is `webhook`.

The first owner gateway is also `webhook`, so owner notifications can be tested without committing to a specific messaging platform.

OpenClaw and Hermes are planned as owner gateway integrations. They should let a user decide from the CLI where owner-facing summaries and escalation messages should be delivered.

Platform-specific customer adapters such as Telegram and WhatsApp can be added after the internal event model is stable.

## First Storage

The MVP uses:

- SQLite for structured operational data.
- Markdown files for long-term customer memory.

The storage layer should be simple enough to inspect manually during development.

## First Runtime

The MVP runs as a local daemon started by the CLI.

The daemon receives webhook events, calls the orchestration layer, persists state, and returns gateway responses.

## First Sandbox

The MVP should include a CLI sandbox so contributors can test the full flow without configuring Telegram, WhatsApp, OpenClaw, Hermes, or any external gateway.

The sandbox should support two roles:

- Customer sandbox: sends test customer messages into the same internal event flow used by real customer gateways.
- Owner sandbox: reads owner summaries, alerts, approval requests, and ticket escalations from the same owner notification flow used by real owner gateways.

The sandbox is part of the MVP because it makes the project easier to develop, demo, and verify as an open-source project.

Expected commands:

```bash
wasila sandbox customer
wasila sandbox owner
```

The customer sandbox should be able to:

- Start a simulated conversation as a new or existing customer.
- Send messages into the `startup_saas` profile.
- Show the AI response returned by the orchestration layer.
- Print the customer ID and ticket ID when created.

The owner sandbox should be able to:

- Show owner summaries generated by the owner agent.
- Show high-priority escalations.
- Show recommended owner actions.
- Acknowledge or comment on an owner notification in a later iteration.
