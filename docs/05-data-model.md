# Data Model

The MVP uses SQLite for structured state, one Markdown file per customer for long-term relationship memory, and Markdown files for business knowledge.

## Storage Principle

Wasila uses a hybrid storage model:

```text
SQLite = operational source of truth
customer.md = human-readable relationship memory
knowledge/*.md = shared business knowledge
```

SQLite should store data that needs to be queried, filtered, joined, audited, or traced.

`customer.md` should store durable qualitative memory for a single customer.

`knowledge/*.md` should store shared business context used across customers.

## Business Knowledge Base

Business knowledge is shared context for all agents in a Wasila project.

It should answer:

- What does the business do?
- What products or services exist?
- What policies should agents follow?
- What support boundaries exist?
- What tone should agents use?
- When should the owner be notified?

Suggested path:

```text
knowledge/
  business.md
  products.md
  policies.md
  support.md
  owner.md
```

Suggested file purposes:

- `business.md`: company overview, audience, value proposition, operating hours, contact rules.
- `products.md`: product or service catalog, plans, pricing notes, features, limitations.
- `policies.md`: refund, billing, privacy, escalation, and customer handling policies.
- `support.md`: troubleshooting steps, known issues, common questions, boundaries.
- `owner.md`: owner preferences, summary format, approval rules, sensitive topics.

The MVP can load all knowledge files into agent context. Later versions can add search, embeddings, versioning, and source-level citations.

## Markdown Memory

Each customer can have a memory file:

```text
data/customers/{customer_id}/customer.md
```

Every customer should have a separate memory file. For example:

```text
data/customers/
  cust_001/
    customer.md
  cust_002/
    customer.md
```

Suggested sections:

```markdown
# Customer Memory

## Identity

## Preferences

## Special Handling

## Important History

## Open Risks

## Owner Notes
```

The memory file is for durable, human-readable context. It should not store secrets or raw full conversation logs.

SQLite remains the operational source of truth for customer identity, channel references, messages, tickets, ticket events, agent runs, owner summaries, and structured metadata.

## Knowledge Versus Customer Memory

Business knowledge belongs to the business and is shared across customers.

Customer memory belongs to a single customer and should capture durable relationship context.

Examples:

- Business knowledge: "Refund requests above IDR 1,000,000 require owner approval."
- Customer memory: "This customer prefers WhatsApp updates and has an unresolved billing concern."

## SQLite Tables

### `customers`

Stores stable customer identity.

Suggested fields:

- `id`
- `display_name`
- `primary_channel`
- `external_refs_json`
- `metadata_json`
- `created_at`
- `updated_at`

### `messages`

Stores inbound and outbound message trace.

Suggested fields:

- `id`
- `customer_id`
- `ticket_id`
- `gateway`
- `direction`
- `body`
- `metadata_json`
- `created_at`

### `tickets`

Stores operational work items.

Suggested fields:

- `id`
- `customer_id`
- `title`
- `status`
- `priority`
- `owner_agent`
- `summary`
- `metadata_json`
- `created_at`
- `updated_at`

### `ticket_events`

Stores append-only ticket history.

Suggested fields:

- `id`
- `ticket_id`
- `actor_type`
- `actor_name`
- `event_type`
- `body`
- `metadata_json`
- `created_at`

### `agent_runs`

Stores orchestration trace.

Suggested fields:

- `id`
- `customer_id`
- `ticket_id`
- `profile`
- `agent_name`
- `task_name`
- `status`
- `input_json`
- `output_json`
- `created_at`

### `owner_summaries`

Stores owner-facing summaries generated by the owner agent.

Suggested fields:

- `id`
- `customer_id`
- `ticket_id`
- `summary`
- `risk_level`
- `recommended_action`
- `created_at`

### `skill_executions`

Stores trace records for every skill an agent calls.

Suggested fields:

- `id`
- `customer_id`
- `ticket_id`
- `agent_run_id`
- `skill_name`
- `execution_level`
- `approval_required`
- `approval_status`
- `input_json`
- `output_json`
- `status`
- `error`
- `created_at`

## MVP Persistence Rules

- Store every inbound and outbound message.
- Treat SQLite as the operational source of truth.
- Keep `customer.md` separate for each customer.
- Create a ticket when the conversation requires tracking.
- Append ticket events instead of overwriting history.
- Store every skill execution.
- Update `customer.md` only when a fact is durable and useful for future treatment.
- Load business knowledge before running customer-facing agents.
- Keep business knowledge maintainable by humans.
- Keep raw secrets out of memory files and summaries.
