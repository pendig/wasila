# CLI Design

The CLI should make Wasila feel like a local operating kit, not a hidden framework.

## MVP Commands

### Initialize A Profile

```bash
wasila init startup_saas
```

Creates local config, profile files, data directories, and SQLite schema.

### Configure Provider

```bash
wasila provider set openai-compatible --base-url https://api.openai.com/v1 --model openai/gpt-4.1-mini --api-key-env OPENAI_API_KEY
```

Stores provider configuration references for any OpenAI-compatible API provider. Secrets should stay in environment variables or local ignored config.

The provider does not have to be OpenAI's official API. It can be any provider, proxy, or local service that supports the OpenAI API shape.

Required provider settings:

- `base_url`
- `model`
- `api_key_env`

### Initialize Business Knowledge

```bash
wasila kb init
```

Creates starter Markdown files under `knowledge/` so agents can understand the business, products, policies, support rules, and owner preferences.

### Add Customer Gateway

```bash
wasila gateway add customer webhook
```

Enables the first generic HTTP webhook gateway for customer conversations.

Now supported customer gateway types are:

```bash
wasila gateway add customer webhook
wasila gateway add customer telegram
wasila gateway add customer whatsapp
```

### Add Owner Gateway

```bash
wasila gateway add owner webhook
```

Enables owner-facing summaries and escalation notifications through a webhook.

Current owner gateway options in Stage 1:

```bash
wasila gateway add owner openclaw
wasila gateway add owner hermes
```

OpenClaw and Hermes are configured as dedicated gateway types and currently resolve through the same webhook transport for bootstrap compatibility.
Customer gateway expansion (`telegram`, `whatsapp`) is now supported in Stage 2 and currently shares the same webhook transport for bootstrap compatibility.

### Start Daemon

```bash
wasila daemon start
```

Starts the local process that receives inbound gateway events and runs orchestration.

### Customer Sandbox

```bash
wasila sandbox customer
```

Starts an interactive CLI session that behaves like a customer channel. Messages entered here should go through the same internal flow as a real customer gateway event.

Optional target design:

```bash
wasila sandbox customer --customer cust_123
wasila sandbox customer --new "Acme Labs"
```

### Owner Sandbox

```bash
wasila sandbox owner
```

Starts an interactive CLI session for owner-facing notifications. This should display owner summaries, risk alerts, ticket escalations, and recommended actions generated by the owner agent.

Optional target design:

```bash
wasila sandbox owner --watch
wasila sandbox owner --latest
```

### Inspect Customer

```bash
wasila customer inspect cust_123
```

Shows structured customer data, open tickets, and the current `customer.md` memory.

### List Tickets

```bash
wasila ticket list
```

Lists active tickets and their current status.

## Later Commands

```bash
wasila profile list
wasila profile add ecommerce
wasila gateway add customer telegram
wasila gateway add customer whatsapp
wasila gateway add owner openclaw
wasila gateway add owner hermes
wasila sandbox conversation replay conv_123
wasila ticket show tick_123
wasila owner summary
wasila memory edit cust_123
```

## CLI Principles

- Commands should be inspectable and predictable.
- Local data should be easy to find.
- Secrets should not be written into docs, templates, or committed files.
- MVP commands should favor clarity over broad configuration power.
